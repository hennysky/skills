# 汇报材料与汇报页

把工作内容做成一份能直接交出去的汇报。**内容层和视觉层分两步做，绝不合并成一步。**

这个 skill 有一个别处没有的东西：**按汇报类型匹配的去 AI 味规则**。同样一句话，在双周汇报里是 AI 味，在述职里可能就是合适的语气；反过来也一样。所以规则不是一张通用清单，是六套。

用户可称它为「汇报 skill」「写汇报」「做汇报材料」。

---

## 什么时候用

用户说这些话时用：写汇报、做汇报材料、双周汇报、周报月报、述职、转正述职、晋升答辩、年度复盘、专项汇报、报销说明、费用申请、立项申请。

也包括：去 AI 味、不要 AI 腔、改得像人写的、汇报太像 AI、帮我润色这份汇报。

**不用**的情况：
- 只是问某个汇报怎么写、聊思路 → 直接聊，不必走流程
- 已经有定稿内容，只要排版 → 跳到第 3 步
- 要 PPTX 文件而非网页 → 走 `ppt-master` skill，本 skill 只出内容和 HTML
- 只想去 AI 味、不涉及汇报（比如改朋友圈、改小红书文案） → 直接用 `renhua` 或 `humanizer-zh`，本 skill 的规则是给商务汇报调过的

---

## 另一种用法：只查 AI 味（已有稿子）

用户手上有写好的汇报，只想让它「不像 AI 写的」，**不要重排结构、不要动内容组织**。

走这条短路：

1. **问类型**（同上，类型决定查哪套专项规则）
2. **读 `references/去AI味规范.md`**，取通用清单 + 对应类型那一节
3. **逐条标注**：指出哪句有问题、属于哪一类、改成什么。**先给诊断，不要直接甩一份改写稿**
4. 用户确认后再出改写版

诊断格式：

```
第 3 条「持续推动市场细分归类工作，取得阶段性进展」
问题：空动词（双周汇报专项禁用），且没有落到三种状态
改成：市场细分归类完成 60%，场景、主题已交付，风格维度卡在源数据缺 12%
```

**为什么先诊断**：直接改写，用户看不出自己原来错在哪，下次还会犯。指出病灶，他才学得会。

## 五步流程

### 第 0 步：确认汇报类型（**必须先问用户**）

汇报类型决定两件事：用哪个骨架、查哪套去 AI 味规则。**猜错的代价很大，所以先确认。**

**如果用户已经说清类型**（如「写双周汇报」「帮我做个述职」）→ 直接用，一句话复述确认即可，不必再问。

**如果用户没说清** → 列出六类让用户选，**不要自己猜**：

```
这份汇报属于哪一类？

1. 双周汇报 —— 固定周期向上级报进展
2. 月度总结 —— 整月汇总、目标完成情况
3. 专项汇报 —— 单一主题深入、方案评审、故障复盘
4. 转正述职 —— 转正、试用期、晋升答辩
5. 年度复盘 —— 年终回顾、明年规划
6. 申请报销 —— 报销、要预算、要资源、立项审批

回数字即可。
```

用户回数字后，**顺便确认读者**（只有一句）：给谁看？直接上级 / 部门负责人 / 老板 / 人事 / 财务 / 跨部门。

读者决定详略和措辞尺度——给人事的必须四项对齐，给财务的必须金额明细，给老板的要更短。

### 第 0.5 步：加载对应的去 AI 味规则

类型确认后，**读 `references/去AI味规范.md`**，取两部分：

1. **第一部分 通用硬禁清单** —— 六类全部适用，共 10 组
2. **第二部分里对应类型的那一节** —— 只读你这一类，不要把六类全背上

每类汇报的 AI 味病灶不同，通用清单挡不住类型特有的毛病：

| 类型 | 要额外防的 |
|---|---|
| 双周汇报 | 过程比结论多、给小事加意义 |
| 月度总结 | 没数字就用形容词补 |
| 专项汇报 | 铺垫式开头、结论藏最后 |
| 转正述职 | 谄媚、假谦虚式不足 |
| 年度复盘 | **"挑战与展望"结构** |
| 申请报销 | 宣传语言、卑躬语气 |

规则在写要点之前就加载好，不是最后再改——**先知道什么不能写，比写完再删省一半力气。**

### 第 1 步：只出骨架，然后停下

产出**只有章节标题 + 每节一句话主旨**，不超过 20 行。

**必须停下来等用户确认，不许自己往下填内容。**

这一步的道理在 `references/内容规范.md` 第 4 节：一次写满，用户只能整体否定重来；先定骨架，骨架错了只改几行标题。

**骨架阶段就要防 AI 味**，最容易犯在标题上：

| ❌ 名词式标题（AI 习惯） | ✅ 判断句标题（人写的） |
|---|---|
| 工作回顾 / 本期概览 | 覆盖范围持平，使用量继续上升 |
| 挑战与展望 | 3 个目标完成 2 个，第三个卡在场景验证 |
| 问题与不足 | 需求判断偏保守，两个低价值需求占了 3 周 |
| 下期计划 | 4 项动作，每项都有可验证的完成标志 |

名词式标题是「分类」，判断句标题是「结论」。前者只说明这块讲什么，后者已经告诉读者答案。

交付时用一句话说明：选了什么场景、按什么逻辑排的、为什么这么排。

### 第 2 步：按确认的骨架填要点

每节 3～5 条，每条不超过 25 字。遵守 `references/内容规范.md` 全部规则，**以及第 0.5 步加载的去 AI 味规则**。

写完过两遍自检，都要过：

1. `references/内容规范.md` 第 6 节的清单（措辞、颗粒度、四项对齐）
2. `references/去AI味规范.md` 第四部分的自检清单（AI 味）+ 用第三部分四个测法抽查三段

**去 AI 味是写的时候就避开，不是写完再洗一遍。** 洗完的稿子会留下痕迹——句子变短了但结构还是 AI 的。

### 第 3 步：生成汇报页 HTML

只在内容定稿后做。步骤：

1. **读 `references/美化规范.md`** —— 这是视觉基线，包含主题路由、字体、5 级字号、8px 栅格、移动端铁律、CDN 白名单、质量清单
2. **按主题路由选风格** —— 汇报类默认走「专业报告 / 方案」入口（浅色底 + 蓝色或紫色主色），述职类可走「投研 / BP」入口（深色 + 紫色）。自己判断，一句话说明选了哪种，不抛问题给用户
3. **从 `references/视觉技法库.md` 取代码** —— 先按规范第 151 行的方法选 2～3 种技法，再 read 对应章节拿 CSS
4. **以 `assets/汇报页模板.html` 为骨架改** —— 里面已实现顶栏、封面、KPI 区、章节容器、页脚口径说明，改内容即可
5. **过质量清单** —— `references/美化规范.md` 最后一节的 14 条，逐条确认

## 三条铁律（不可破，破了就重写）

详见 `references/内容规范.md`，这里只列结论：

1. **不说「问题」，说「现状 / 方向 / 价值」** —— 现状只写事实和数字，不写评价词，让读者自己得出结论
2. **不点领导名** —— 涉及责任和支持，写部门或角色，不写人名
3. **括号里的一律删掉** —— 重要的升成正文，不重要的删，没有第三种处理

---

## 硬性交付标准

- 每处「现状」必须有具体数字
- 每节要点 ≤ 5 条，每条 ≤ 25 字
- 结论放最前面，不放最后面
- 章节标题用判断句，不用名词
- 全文无「赋能」「抓手」「闭环」这类抽象词
- 全文无「不是 A 而是 B」「真正/本质上」「显著提升（不带数字）」
- 每段末尾没有升华句
- 涉及绩效时，成绩／差距／原因／策略四项必须一一对应

## 常见坑

- **跳过第 0 步自己猜类型** —— 类型猜错，骨架和去 AI 味规则会一起错。用户没说清就列六类让他选
- **第 1 步就填满内容** —— 最容易犯。骨架阶段写超过 20 行就是失控
- **把「现状」写成抱怨** —— 只要出现「严重」「不足」「混乱」，就不是现状，是评价
- **报销类一上来写金额** —— 应先证明不解决的后果，金额放后面
- **写完再洗 AI 味** —— 顺序错了。规则要在写之前加载，洗完的稿子结构还是 AI 的
- **给全年汇报套「挑战与展望」** —— AI 生成文本最典型的标志，换成「未完成与反思」
- **标题全用名词** —— 「工作回顾」「问题与不足」是分类不是结论，改判断句
- **汇报页做成 PPT 风格** —— 每屏「居中标题 + 项目符号」是 PPT 思维，`references/美化规范.md` 明确禁止
- **编数字** —— 任何数字都要能说出出处。报销单和目标完成率上的数字会被核对
